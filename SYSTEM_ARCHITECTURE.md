# Electronic Document Management System architecture

React 18, Vite and React Router provide the existing frontend. RepositoryUI reuses the existing panel, table, badge and form design. EnterpriseLayout now supplies document-only navigation. EnterprisePages contains repository browsing, dashboard, collections, configuration, local activity and role inspection. DocumentCapture preserves OCR/text extraction; RepositoryDetail and PdfPreview provide document metadata, actual file access, retained versions and preview.

`enterprise.ts` retains the original persistence keys and historical data model. Its normalisation preserves IDs, versions, binaries, business references, old status and holds, adding a distinct storage status. Historical workflow fields survive migration as data only; workflow mutations and operational UI routes were removed. `repository.ts` implements document permissions, metadata validation, configuration, search, collections, file access, upload rollback, versions, archive and soft removal. `file-validation.ts` checks formats, signatures, sizes and Office package structure.

Metadata remains in localStorage and attachments in IndexedDB for fictional local evaluation. The read-only frontend activity interface is not tamper protection. The permission checks are not a production security boundary. No live organisational database or file provider is connected.

The proposed permanent implementation preserves Supabase. The migration introduces dedicated profiles, documents, immutable version manifests, classification rules, settings and server-written activity. RLS evaluates real authenticated identities, departmental scope and confidentiality. The new private bucket denies ordinary direct access even if other broad storage policies exist. The authenticated Edge file broker uses the actor's RLS-scoped client for business records and a server-only service credential for guarded file access and compensation. A service-only audit function records retrieval events. The source is not yet deployed or tested against a Supabase database.

Before operational use: configure SSO and approved profiles, review/apply the schema in an isolated project, test direct REST/storage attacks across roles, connect the frontend adapter, migrate approved documents with checksum reconciliation, validate the file broker, add malware scanning and recovery, review dependency advisories and perform browser/accessibility testing. Existing KV handlers remain preserved and unconnected; they are not the secured repository service.
